# One finite Office development commitment

AP11 adds a named Temporal parent for the accepted Office reconciliation and its
dependent AP08 handoff. It reuses DevelopmentTask, separate native review and the
existing protected Publisher. It cannot choose another business goal. Registering
this code is not activation, and two child deliveries are not whole-goal approval.

The host freezes the owner authority, separately reviewed G1–G10 acceptance,
exact Runtime/Office revisions and resource contract outside candidates. The
application reserves at most48 model processes in total, including preparation,
interactive handover, reviews and diagnosis. Each logical implementation has at
most6 attempts across task identities. Crashes never refund reservations.
Construction before application is reported separately.

`python -m scripts.install_ap11` stages only integrated source and three selected
private inputs. It copies the existing AP10 context bytes exactly. Selection and
LaunchAgent replacement remain explicit, separately reviewed operator actions.
Preserve/read back the database, old pointer, plist, schedule and histories before
switching. Drain old AP10 actions. Rebind only the schedule action's config hash;
retain its spec, policy, state and history. Verify native attachment and rollback
readiness. No checkout branch changes an active release.

The AP11 LaunchAgent profile uses the same existing host gh authentication for
Git transport and API calls. It copies no token and changes no account grant.
Model/candidate environments exclude the Git-helper variables and credentials.

A named one-shot synthetic capacity trial uses the actual queue, single activity
slot and admission reader. It occupies the slot, then yields through a Temporal
timer before watch-shaped stages run with AP10's ordinary native bounds. After
the fixture watch completes, pause only its fixture schedule so remaining build
work can finish. Preserve actual timing and the real AP10 before/after status.
This is capacity evidence, not supplier intake or model/business evidence.

After qualification and explicit scope initialization, the operator runs
`python -m runtime.development_control interactive-start` in a real terminal.
The already-waiting native parent receives A from a genuine interactive CLI
session. That session independently prepares A from selected sources; no B draft
is supplied. The operator may close the TUI after its completed turn. Context,
operator input, actual native identity, history and process cleanup are private
handover evidence. Only after verified exit does the parent independently review
and freeze A, build/review/integrate it, and derive B from actual integrated A.
No observer instruction or continuation signal may occur during the qualified
independent interval through B preparation and start.

`status` is a dated read and never starts models, signals or publishes. `pause
--reason ...` persists a block on new work but permits an already started child to
finish its accepted review/publication. `resume --reason ...` is an explicit
operator action after diagnosis. `stop --reason ...` closes new starts/effects
before cancelling only this scope's native children and parent; repeated stop
reconciles incomplete cancellation without reopening the gate. Missing native
work remains missing evidence. Stopped/revoked/exhausted scopes cannot reopen.

A missing review or host/access fault cannot automatically become a candidate
repair. Automatic repair requires a real independently bound rejection; the
same finding cannot be reused by paraphrasing a diagnosis. Other recovery needs
actual host inspection through existing native recovery. Uncertain remote
mutations require readback, never blind repetition.

The final native reviewer receives actual task observations, native histories,
scope history, fresh remote integration readback and selected hash-bound private
qualification evidence. Missing evidence waits; non-approval leaves the scope
paused and whole-goal status false. The final reviewer must differ from all prior
driver, implementer and code-review identities. Only approval permits the host
to stop this finite scope and preserve final readback. AP10 is not stopped.

The candidate cannot edit its host recipe, active driver, publication authority
or overall acceptance. Candidate code executes only in the existing sandbox;
models propose data, not executable host verification. Earlier audit statuses
remain unchanged. Aquarium and every next development goal require a separate
accepted decision.
